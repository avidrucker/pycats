# CPU jitter-jump — root-cause findings (#927)

**Ticket:** #927 (child of #925 CPU-behavior-fidelity epic). **Role:** RESEARCH (investigation — reproduce + root-cause, no fix).
**Repro artifact:** `repros/jitter_jump_instrument.py` (read-only; subclasses `AttackerController`, edits no shipped code).
**As-of:** commit on `br-banana/pycats-927`, 2026-07-31.

## TL;DR

The jitter is **one root cause, not the interaction the ticket hypothesised**: the #369
jump-toward-elevated-target pulse (`AttackerController.decide`, the
`dy < -FOE_ABOVE_DY and on_ground and adx < JUMP_UP_NEAR_ADX` block) holds `up`
**continuously for the first `JUMP_UP_STUCK_MAX` (90) frames**. Because a jump only fires on a
fresh press **edge** (`fighter_input.handle_actions`: `jump_pressed = self._pressed(pressed,
"up")`) *and* only from a jumpable state, whenever the initial `up` press is consumed without
producing a jump — the edge lands during a **dodge / hitstun** state, or `up` is already held on
entry — the continuous 90-frame hold then **blocks any re-press**, stranding the bot grounded
under the target holding a dead `up`. It shuffles horizontally for ~90 frames, then at
`_jump_up_stuck == 91` the pulse finally releases `up` for one frame and re-presses → one late
hop. Airborne resets the counter; the bot lands and the cycle repeats every ~80–100 frames. That
repeated *stuck-then-hop* is what reads as "keeps jumping over and over."

- **Anti-stall (#368) never fired** in the repro — ruled out.
- **Ledge-getup** contributed 17 of 292 `up`-frames (real ledge grabs), a minor side actor, not the jitter.
- **Recover / edge-hog / edge-guard are dead code in this repro** — `run_battle`'s two-controller
  path calls `c(p1, p2, f, attacks)` with **no `ledges` arg**, so `ledges=None` disables all three.

## 2. The specific branch and conditions

The only `up`-emitter that produces the jitter is the jump-toward block in
`AttackerController.decide`:

```python
if dy < -FOE_ABOVE_DY and a.fighter.on_ground and adx < JUMP_UP_NEAR_ADX:
    self._jump_up_stuck += 1
    if self._jump_up_stuck <= JUMP_UP_STUCK_MAX or self._jump_up_stuck % 2 == 0:
        held.add(keys["up"])
else:
    self._jump_up_stuck = 0
```

The pulse re-arm logic behaves in three regimes:

- **`_jump_up_stuck` 1..90** → `up` held **every frame** (by design "byte-identical to the old
  always-hold", #369). One press edge at the transition into holding; **none after**.
- **`_jump_up_stuck` == 91** (odd, > 90) → `up` **released** for one frame.
- **`_jump_up_stuck` >= 92** → alternates held (even) / released (odd) → a fresh press edge every
  other frame → a jump attempt every ~2 frames (the classic rapid bounce, latent here).

The FSM half that makes the hold pathological (`fighter_input.handle_actions`):

```python
jump_pressed = self._pressed(pressed, "up")   # requires a fresh press EDGE
...
if (jump_pressed and ... and p.state not in ("dodge", "hurt", "stun", "helpless")):
    p.fighter.vel.y = p.fighter.jump_vel      # jump only here
```

A jump needs **both** a fresh `up` edge **and** a jumpable state. Controller edge detection lives
in `BaseController.__call__`: `pressed = held - self._prev`. So a held `up` carried across frames
generates **no** edge.

The `up` press at f320 is consumed by the **dodge** state (the Lv7 reactive evade roll, #338),
proving the interaction the ticket asked about is real — but it is the *trigger*, and the #369
hold window is the *amplifier* that turns a single eaten press into an ~90-frame lockout. A
secondary, milder horizontal jitter is visible in the same window: `adx` oscillates across the
`standoff ± 8` band (Lv7 `standoff`=32 → 24..40), so the `move` key toggles toward/none/away
frame-to-frame.

## 3. One cause or an interaction; when it triggers vs stays quiet

**Single root cause:** the #369 `_jump_up_stuck` "hold for the first 90 frames" rule, interacting
with edge-based jump detection (`pressed = held - prev`) and the FSM's non-jumpable states. The
counter is keyed on "grounded + wanting up", but its edge management is wrong for the case where
the initiating `up` press does not produce a jump: it should **re-arm the press the instant the
fighter becomes jumpable**, and instead it suppresses re-press for 90 frames.

**Triggers when:** the target stays sustained `> FOE_ABOVE_DY` (30 px) above and within
`JUMP_UP_NEAR_ADX` (120 px) horizontally, while the bot repeatedly lands back grounded — i.e. the
target is on a platform one hop away, or is being juggled, or a standoff settles under a platform
— **and** the `up` press coincides with a non-jumpable state (dodge from the #338 evade roll;
hurt/stun from hitstun; helpless). The dodge coincidence is frequent at Lv7/Lv9 (evade_chance
0.15/0.30).

**Stays quiet when:** the target is level-or-below (`dy >= -30`, guard false), far horizontally
(`adx >= 120`, guard false), or the very first `up` press lands in a jumpable state — then the bot
jumps on frame 1, `on_ground` goes False, `_jump_up_stuck` resets, and behaviour is the normal
single clean jump (this is the common case and the one #369 kept byte-identical).

## 4. Golden-safety constraints on a future fix

- **The jump-toward block is NOT gated on `self.level`.** It runs on the level-less/default
  `AttackerController` (the chase bot) exercised by many golden/parity/behaviour tests —
  `test_dual_controller`, `test_bot_match_resolves`, `test_watch_vs_duration`, `test_reach_aware`,
  and others. The `JUMP_UP_STUCK_MAX = 90` constant was deliberately chosen (#369 comment) so the
  first-90-frames hold is "byte-identical to the old always-hold" and ordinary + seeded battles do
  not move.
- **Consequence for the fix:** any change to the `_jump_up_stuck <= 90` window (e.g. re-arming the
  press as soon as the fighter is grounded-and-jumpable after an eaten press) **will perturb the
  level-less golden path**. The architect (#925 child 3) must choose one of:
  1. **Gate the new re-arm logic to leveled bots** (`self.level is not None`) — mirrors the
     existing level gates on smash (#714), tilt-convert (#292), and anti-stall (#368); keeps the
     default path byte-identical → golden-safe.
  2. **Change the default path too and regenerate goldens** — larger blast radius; the sim goldens
     and the `test_battle_screen_render` render-parity oracle would need re-baselining.
- The anti-stall (#368) and ledge branches need no change for the jitter; leave them out of scope.
- The `run_battle` two-controller path passing no `ledges` (so recover/edge-hog/edge-guard are
  dead in CPU-vs-CPU) is a **separate** latent gap — flagged here, not fixed; it belongs to the
  epic's later stages if those behaviours are wanted in leveled duels.
